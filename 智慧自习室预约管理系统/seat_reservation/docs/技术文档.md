## 一、部署

本文档描述如何在 Windows 与 Linux 上部署本系统。系统为单体服务，只需要 Python 运行时与一个可写的数据库目录，不需要额外安装数据库服务。

### 1. 部署前提

| 项 | 要求 |
|---|---|
| Python | 3.11 及以上（开发验证使用 3.13） |
| 操作系统 | Windows 10/11、Windows Server 2019+、主流 Linux 发行版 |
| 内存 | 512 MB 起，建议 1 GB |
| 磁盘 | 程序约 30 MB；数据库按每万条预约约 20 MB 估算 |
| 端口 | 默认 8010，可改；对外应经反向代理暴露 443 |
| 网络 | 学生与管理员通过浏览器访问，不需要安装客户端 |

数据库文件必须放在**本地磁盘**，不要放在网络共享盘上：SQLite 的 WAL 依赖文件锁，网络文件系统会导致数据损坏。

### 2. Windows 部署

以安装在 `D:\apps\seat_reservation` 为例。

```powershell
# 1. 准备目录与虚拟环境
cd D:\apps\seat_reservation
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

# 2. 生产配置（写入 .env 由启动脚本读取，或直接在服务里设环境变量）
$env:SEAT_ENV = "production"
$env:SEAT_COOKIE_SECURE = "true"
$env:SEAT_DB_PATH = "D:\apps\seat_reservation\var\seat_reservation.db"
$env:SEAT_HOST = "127.0.0.1"
$env:SEAT_PORT = "8010"
$env:SEAT_ACS_TOKEN = "<闸机令牌，无则留空>"

# 3. 初始化数据库（不要加 --demo）
.\.venv\Scripts\python.exe run.py init-db

# 4. 自检
.\.venv\Scripts\python.exe run.py doctor

# 5. 前台试运行，确认可访问后按 Ctrl+C 停止
.\.venv\Scripts\python.exe run.py serve
```

#### 注册为 Windows 服务

使用 NSSM 或 `sc.exe` 均可。以 NSSM 为例：

```powershell
nssm install SeatReservation "D:\apps\seat_reservation\.venv\Scripts\python.exe" "D:\apps\seat_reservation\run.py serve"
nssm set SeatReservation AppDirectory "D:\apps\seat_reservation"
nssm set SeatReservation AppEnvironmentExtra SEAT_ENV=production SEAT_COOKIE_SECURE=true SEAT_DB_PATH=D:\apps\seat_reservation\var\seat_reservation.db
nssm set SeatReservation Start SERVICE_AUTO_START
nssm start SeatReservation
```

服务启动后确认 `http://127.0.0.1:8010/api/health` 返回 `"status":"ok"`。

如果不用 NSSM，也可用“任务计划程序”创建“计算机启动时”触发的任务，操作指向一个调用上述命令的 `.cmd` 文件。注意勾选“不管用户是否登录都要运行”。

以 `/opt/seat_reservation`、运行用户 `seat` 为例。


### 4. 反向代理与 HTTPS

系统必须部署在 HTTPS 之后。原因是会话 Cookie 在 `SEAT_ENV=production` 时带 `Secure` 标记，纯 HTTP 下浏览器不会回传，表现为“登录成功但立刻退出”。

Nginx 示例：

```nginx
server {
    listen 80;
    server_name seat.example.edu.cn;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl http2;
    server_name seat.example.edu.cn;

    ssl_certificate     /etc/nginx/ssl/seat.crt;
    ssl_certificate_key /etc/nginx/ssl/seat.key;
    ssl_protocols       TLSv1.2 TLSv1.3;

    client_max_body_size 2m;

    location / {
        proxy_pass         http://127.0.0.1:8010;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_read_timeout 60s;
    }
}
```

反向代理必须透传 `X-Forwarded-For`，否则审计日志里的来源 IP 会全部变成 `127.0.0.1`。

### 6. 升级流程

```bash
# 1. 先备份
python run.py export reservations --out backup/reservations-$(date +%F).csv
# 数据库文件按 第二部分 的方式复制

# 2. 停止服务
sudo systemctl stop seat-reservation

# 3. 替换代码后执行迁移（迁移是幂等的，重复执行安全）
sudo -u seat .venv/bin/python run.py init-db

# 4. 自检并启动
sudo -u seat env SEAT_DB_PATH=/var/lib/seat_reservation/seat.db .venv/bin/python run.py doctor

```

健康检查返回的 `db.schema_version` 应与代码中的迁移版本一致。

### 7. 回滚

1. 停止服务；
2. 恢复上一版本的代码目录；
3. 若本次升级包含数据库迁移，必须同时恢复升级前的数据库备份（旧代码不认识新表结构）；
4. 启动并自检。

因此**每次升级前都必须备份数据库**，这是回滚能否成立的前提。

### 8. 常见部署问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动即退出，提示必须开启 `SEAT_COOKIE_SECURE` | `SEAT_ENV=production` 但未设 Cookie Secure | 设置 `SEAT_COOKIE_SECURE=true` 并确保经 HTTPS 访问 |
| 登录成功但立刻退出 | 通过 HTTP 访问，`Secure` Cookie 未回传 | 走 HTTPS，或临时把 `SEAT_ENV` 改为 `development` 排查 |
| 启动报 `database is locked` | 多个实例指向同一个库文件，或库在网络盘 | 只保留一个实例；数据库移到本地磁盘 |
| 审计日志里 IP 全是 127.0.0.1 | 反向代理未透传 `X-Forwarded-For` | 按上文补充代理头 |
| 到点未释放座位 | 调度器被关闭，或系统时间不准 | 检查 `SEAT_SCHEDULER_ENABLED`、`/api/admin/scheduler` 与 NTP |
| 静态页面 404、接口正常 | 反向代理只转发了 `/api` | `location /` 整体转发，不要只转发接口前缀 |

## 二、备份与恢复

本系统的全部业务数据都在一个 SQLite 文件里，备份的核心就是**在一致的前提下复制这个文件**。看似简单，但有三个必须遵守的前提，否则备份可能是坏的。

### 1. 三个前提

**一、不能只复制 `.db` 文件。**
数据库开启 WAL 模式后，已提交但尚未 checkpoint 的数据在 `-wal` 文件里。只复制 `.db` 会丢掉最近的事务。

**二、不能在有写入时直接 `cp`。**
复制过程中若有事务提交，得到的可能是撕裂的文件。在线备份必须用 SQLite 的备份接口。

**三、恢复时必须三个文件一起处理。**
恢复旧 `.db` 时，如果目录里还留着新的 `-wal`，SQLite 会把新 WAL 应用到旧库上，直接损坏数据。

### 2. 在线备份（推荐，服务不用停）

使用 SQLite 的在线备份接口，能在有写入的情况下取得一致快照：

```bash
cd /opt/seat_reservation
mkdir -p backup

python - <<'PY'
import sqlite3, datetime, pathlib

src_path = pathlib.Path("var/seat_reservation.db")          # 按实际 SEAT_DB_PATH 修改
out = pathlib.Path("backup") / f"seat-{datetime.date.today():%Y%m%d-%H%M}.db"
src = sqlite3.connect(f"file:{src_path}?mode=ro", uri=True)
dst = sqlite3.connect(out)
with dst:
    src.backup(dst)
dst.execute("PRAGMA journal_mode=DELETE")   # 备份文件用单文件模式，便于异地保存
dst.close(); src.close()
print("backup ->", out)
PY
```

备份完成后校验完整性，不通过就不能算备份成功：

```bash
python - <<'PY'
import sqlite3, glob
path = sorted(glob.glob("backup/seat-*.db"))[-1]
conn = sqlite3.connect(path)
print(path, conn.execute("PRAGMA integrity_check").fetchone()[0])
print("tables:", conn.execute("SELECT count(*) FROM sqlite_master WHERE type='table'").fetchone()[0])
conn.close()
PY
```

期望输出 `ok`。表数量为 18：17 张业务表加 1 张迁移记录表 `schema_migrations`（由 `database.py` 创建，
记录已执行的迁移版本）。注意不是 `sqlite_sequence` —— 本库没有 AUTOINCREMENT 表，不会出现该表。

### 3. 冷备份（停机，最简单）

```bash
sudo systemctl stop seat-reservation
cp var/seat_reservation.db      backup/seat-$(date +%F).db
cp var/seat_reservation.db-wal  backup/seat-$(date +%F).db-wal 2>/dev/null || true
cp var/seat_reservation.db-shm  backup/seat-$(date +%F).db-shm 2>/dev/null || true
sudo systemctl start seat-reservation
```

三个文件必须同名同批。恢复时也一起还原。

### 4. 逻辑备份（跨版本、可读）

结构变更或需要人工核对时，导出 CSV：

```bash
python run.py export reservations --out backup/reservations-$(date +%F).csv
python run.py export violations   --out backup/violations-$(date +%F).csv
python run.py export audit        --out backup/audit-$(date +%F).csv
```

CSV 带 UTF-8 BOM，Excel 可直接打开。注意：CSV 只用于核对与归档，**不能替代数据库备份**，它不含密码哈希、会话与内部标识关系。

### 5. 定时备份

Linux（每天 02:30，保留 30 天）：

```cron
30 2 * * * cd /opt/seat_reservation && /opt/seat_reservation/.venv/bin/python scripts/backup.py >> var/backup.log 2>&1
30 3 * * * find /opt/seat_reservation/backup -name 'seat-*.db' -mtime +30 -delete
```

其中 `scripts/backup.py` 已随项目提供：

```bash
python scripts/backup.py --db /var/lib/seat_reservation/seat.db --out /opt/backup --keep 30
```

脚本会做在线备份、立即 `integrity_check`，校验不通过时以非零码退出，便于定时任务告警；`--keep` 大于 0 时才清理更早的备份，**不传就一个文件都不删**。

Windows（任务计划程序）：

- 触发器：每天 02:30；
- 操作：`D:\apps\seat_reservation\.venv\Scripts\python.exe D:\apps\seat_reservation\scripts\backup.py`；
- 起始于：`D:\apps\seat_reservation`。

备份应复制到**另一块磁盘或另一台机器**。同盘备份在磁盘故障时一起丢失。

### 6. 恢复步骤

```bash
# 1. 停服务，确保没有进程持有数据库
sudo systemctl stop seat-reservation

# 2. 把当前库移走（不要直接覆盖，留作事后取证）
mv var/seat_reservation.db     var/seat_reservation.db.broken-$(date +%F-%H%M)
mv var/seat_reservation.db-wal var/seat_reservation.db-wal.broken-$(date +%F-%H%M) 2>/dev/null || true
mv var/seat_reservation.db-shm var/seat_reservation.db-shm.broken-$(date +%F-%H%M) 2>/dev/null || true

# 3. 还原备份（若备份是单文件模式，只需还原 .db）
cp backup/seat-20261030-0230.db var/seat_reservation.db

# 4. 校验
python - <<'PY'
import sqlite3
conn = sqlite3.connect("var/seat_reservation.db")
print("integrity:", conn.execute("PRAGMA integrity_check").fetchone()[0])
print("schema:", conn.execute("PRAGMA user_version").fetchone()[0])
print("reservations:", conn.execute("SELECT count(*) FROM reservations").fetchone()[0])
conn.close()
PY

# 5. 自检并启动
python run.py doctor
sudo systemctl start seat-reservation
curl -s http://127.0.0.1:8010/api/health
```

`integrity` 必须为 `ok`，`schema` 应与目标版本一致。健康检查返回 `"status":"ok"` 才算恢复完成。

### 8. 保留与清理

- 业务数据保留 2 年（NFR-06）；
- 终态预约可用 `python run.py prune --days 730 --dry-run` 预览，确认后再去掉 `--dry-run` 执行；
- 审计日志由触发器保护，**不提供删除接口**，清理只能通过归档整个数据库实现；
- 备份文件按 30 天滚动保留即可，跨学期的重要节点建议单独归档一份。

### 9. 常见错误

| 做法 | 后果 |
|---|---|
| 只复制 `.db`，忽略 `-wal` | 丢失最近事务，停机前的预约消失 |
| 运行中直接 `cp` 数据库 | 可能得到撕裂文件，`integrity_check` 报错 |
| 恢复时只还原 `.db`，保留新 `-wal` | 新 WAL 套到旧库上，数据错乱 |
| 用 CSV 导出当唯一备份 | 丢失密码、会话与内部关联，无法完整恢复 |
| 备份与数据库同盘 | 磁盘故障时同时丢失 |
| 从未做过恢复演练 | 真出事时才发现备份不可用 |

## 三、安全设计

本文档说明系统在认证、会话、授权、凭证、审计与数据保护上的实现方式，以及部署方需要承担的安全责任。凡是"应用已实现"与"依赖部署配置"的内容分开标注，避免把责任混淆。

### 1. 认证

**密码存储**：PBKDF2-HMAC-SHA256，迭代 260000 次，每个账号 16 字节随机盐，存储格式 `pbkdf2_sha256$迭代次数$盐$摘要`。迭代次数写在记录里，后续可整体升级而不影响旧密码校验。

**密码校验**：使用恒定时间比较，避免通过响应时间推断摘要。账号不存在与密码错误返回同一个错误码，不泄露账号是否存在。

**登录限流**：同一来源 IP + 账号在 5 分钟内失败 5 次后锁定 5 分钟，返回 429。计数保存在进程内存中，**单实例有效**；多实例部署时需要改为共享存储，否则限流会被绕过。

**密码强度**：修改密码时要求新密码不少于 8 位；系统不强制复杂度规则，由部署方在账号发放环节约束。

### 2. 会话

| 项 | 实现 |
|---|---|
| 会话标识 | 32 字节随机令牌，Cookie 传递 |
| 落库形式 | 只存令牌的 SHA-256 摘要，数据库泄露无法直接复用会话 |
| Cookie 属性 | `HttpOnly`、`SameSite=Lax`、`Path=/`；生产环境加 `Secure` |
| 空闲超时 | 默认 30 分钟，每次请求刷新，可通过 `SEAT_SESSION_IDLE_MINUTES` 调整 |
| 绝对超时 | 默认 8 小时，到期强制重新登录 |
| 失效时机 | 主动退出、修改密码、账号被停用、超时 |

修改密码会使该账号的**全部**历史会话失效，这是刻意设计：密码泄露后改密即可踢掉攻击者。

`SameSite=Lax` 意味着跨站 POST 不会携带会话 Cookie，配合下面的 CSRF 双提交形成两层防护。

### 3. CSRF

采用双提交校验：

- 登录成功后同时下发两个 Cookie：`seat_session`（HttpOnly）与 `seat_csrf`（可读）；
- 所有非 GET 请求必须带 `X-CSRF-Token` 头，值等于 `seat_csrf`；
- 服务端比对请求头与 Cookie，不一致直接返回 403 `CSRF_FAILED`。

豁免路径只有两个：`/api/auth/login`（尚无会话）与 `/api/acs/*`（设备端无浏览器 Cookie，改用独立令牌）。

前端在 `fetch` 封装里统一注入该头，业务代码不需要逐处处理。

### 4. 授权

权限在**服务端逐请求**校验，实现为 `PR-01`～`PR-18` 的规则集：

- 每个用例先在引擎层 `_require(actor, {允许的角色}, "PR-xx")`，不满足抛 `Forbidden`；
- 界面隐藏入口只是体验优化，**不作为权限手段**；
- 越权请求必须产生**零数据变化**，且不写审计日志（避免攻击者用失败请求污染日志）。

数据可见范围另行约束，例如：

- 学生只能读取本人的预约、违规、信用流水；
- 教师只能读取本班汇总，取明细直接 403；
- 管理员的查询按角色限定在业务必要字段内。

### 5. 签到凭证

- 10 位 Crockford Base32 字符（排除易混淆的 `0/O/1/I`），约 49 bit 熵；
- 有效期 60 秒，过期需重新签发；
- **一次性**：使用后立即失效，重复提交返回已使用；
- 校验时同时核对预约归属、预约状态与时间窗，三者任一不满足都拒绝；
- 闸机端点 `/api/acs/check-in` 额外要求 `X-ACS-Token`，令牌来自 `SEAT_ACS_TOKEN`，用恒定时间比较。

凭证只在签发时返回一次明文，数据库仅存摘要。

### 6. 审计

- `audit_logs` 由数据库触发器禁止 `UPDATE` 与 `DELETE`，只能追加；
- 记录字段：操作人、角色、动作、对象类型与对象 ID、变更前后值、时间、来源 IP；
- 覆盖封禁/解封、强制释放、手动违约、参数变更、角色变更、申诉审核、投诉办结、评价回复、拉黑/解封、自动拉黑；
- 查询权限仅系统管理员（PR-15）；
- 导出为 CSV 时也受同一权限约束。

来源 IP 取自反向代理透传的 `X-Forwarded-For`。**如果代理未配置透传，审计里的 IP 会全部是 127.0.0.1**，等于失去溯源能力，这是部署时必须核对的项。

### 7. 数据保护

| 数据 | 保护措施 |
|---|---|
| 密码 | 单向哈希，不可逆；接口与日志均不返回 |
| 会话令牌 | 只存摘要；Cookie HttpOnly |
| 学生个人信息 | 仅姓名、学号、班级、院系；学生只见本人，教师只见汇总 |
| 预约与违规 | 他人仅可见"占用/空闲"，不含身份 |
| 日志 | 不记录密码、令牌、凭证明文 |
| 数据库文件 | 依赖操作系统文件权限；部署时数据库目录只对运行用户可写 |

**个人信息最小化**：系统不采集身份证号、手机号、住址等字段。若后续对接统一身份认证需要扩展字段，应同步更新数据字典与权限矩阵。

### 8. 部署方责任

以下内容应用本身无法保证，必须由部署环境落实：

1. **全站 HTTPS**。生产环境 `SEAT_COOKIE_SECURE=true` 时，纯 HTTP 访问会导致登录后立刻退出。证书与 TLS 配置由部署方负责。
2. **数据库文件权限**。确保只有运行用户可读写，必要时对磁盘做加密。
3. **备份文件保护**。备份包含全量业务数据与密码哈希，应与生产库同等保护，异地存放时建议加密。
4. **操作系统与依赖更新**。定期更新 Python 运行时与 `requirements.txt` 中的依赖。
5. **时间同步**。签到窗口、超时释放、凭证有效期都依赖系统时间，必须开启 NTP。
6. **初始账号**。交付后立即创建正式系统管理员，禁用或删除演示账号，生产库不得执行 `seed`。

### 9. 已知限制

- 登录限流为进程内存实现，多实例部署时失效；
- 无多因素认证；
- 无接口级签名与防重放（除 ACS 令牌外），依赖 HTTPS 与会话机制；
- 审计日志不可删除，长期运行需要归档整库，而不是按行清理；
- 未做渗透测试与代码审计，安全结论仅覆盖已列出的机制。

如需对外提供接口给第三方系统，应先补充令牌签发、作用域限制与调用审计，当前未实现。
