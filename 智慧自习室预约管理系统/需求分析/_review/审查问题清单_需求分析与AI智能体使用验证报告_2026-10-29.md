## 3. P0 阻断性问题

### R-01 测试与证据不可复现（最高优先级）

**现象**

在 `prototype` 目录执行报告写的验收命令：

```bash
cd prototype && node --test --test-reporter=tap tests/*.cjs
```

实际输出（2026-10-29）：

```text
1..62
# tests 62
# pass 27
# fail 35
# cancelled 0
# skipped 0
# todo 0
```

**与报告的冲突**

| 位置 | 报告写法 | 实际 |
|---|---|---|
| `attachments/evidence/E-TEST-01-自动化测试运行日志.md:13` | `tests 46 / pass 46 / fail 0` | 46 条领域测试中有 31 条失败 |
| `attachments/evidence/E-TEST-02-页面交互走查运行日志.md:13` | `tests 62 / pass 62 / fail 0` | 62 条中 35 条失败 |
| `B-AI智能体使用验证报告.md:94` | “46/46 通过” | 不成立 |
| `B-AI智能体使用验证报告.md:110` | “62 条测试全绿” | 不成立 |
| `B-AI智能体使用验证报告.md:191` | “62 条测试全部通过（46+16，0 失败）” | 不成立 |
| `prototype/README.md:16` | “60 条全部通过（44+14+2）” | 条数与结果均不成立 |

**根因**

- `prototype/seed.js:42-56` 用 `new Date()` 作为种子数据基准，预置预约的 ID（如 `RYYYYMMDD-02`）和日期随运行当天变化；
- `prototype/tests/domain.test.cjs:13` 固定 `D = '2025-10-20'`，`:23` 的 `fresh()` 调用 `createSeedState()` 时没有传入固定时间；
- `prototype/tests/ui.test.cjs:296`、`:303` 硬编码 `2025-10-21`；
- `prototype/tests/_probe.test.cjs` 的 T45/T46 引用固定预约 `R20251020-02`。

因此，测试只在“运行当天恰好是 2025-10-20”时才能对上种子数据；在当前提交版本上，T45 找不到 `R20251020-02`，T04 的“当日第 3 个时段”基线也随日期漂移。

**证据文件自身的矛盾**

- `E-TEST-01:15` 写“测试为纯函数式、时间由参数注入，不依赖真实时间与网络”，与 `seed.js` 的 `new Date()` 直接矛盾；
- `E-TEST-01:12`、`E-TEST-02:12` 声称“原型内模拟时钟为 2025-10-20”，但当前运行原型显示的是 2026-10-29；
- 如果证据确实是在 2026-10-15 跑的，那么按提交的 `seed.js`，种子日期应是 2026-10-15，测试仍会失败。这说明**证据生成时的代码与最终提交的代码不是同一版本**，违反了模板“配套文件与最终版本保持一致”的要求。

**影响范围**

- E-08、E-09 两份核心证据；
- A.6 的 PV-01~PV-12 “通过，功能验证”；
- B.3 的“完成标准：自动化测试……全部通过（0 失败）”；
- B.2 的 AI-04/AI-05 “独立核验方法、范围与结果”；
- A.7 中 V-03/V-04/V-05 的“全套 60/62 条测试通过”复核结论。

**建议修复方向（未实施）**

1. 给测试一个固定时钟：`fresh()` 改为 `seed.createSeedState('2025-10-20T08:00:00')`，UI 测试的 `boot()` 同样固定；
2. 或者让测试从 `SRSSeed.TODAY/CLOCK_START` 派生日期与预约 ID，不再硬编码 `2025-10-20/21`；
3. 重跑 `node --test tests/*.cjs`，确认 62/62；
4. 重新生成 E-TEST-01/02，并把 README、B.2、B.3、A.7 的条数与结果同步；
5. 如果原型必须保留“按真实日期演示”的行为，应增加“测试专用固定时钟”入口，而不是让测试依赖真实日期。

> 这个问题不属于“格式”问题，但它直接决定 A.6/B.3 的“已验证”结论是否成立。评审只要照着命令跑一次就会暴露，建议优先于所有文字修改。
