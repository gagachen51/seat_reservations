# B 模块安全整改测试用例

> 文档口径（v2.0.3，2026-11-26）：当前发布版本 **v2.0.3**；`pytest` **499 passed / 1 skipped**，Node **43 passed**；用户启动方式统一为安装 `setup.exe`。本文历史章节中的旧版本/测试数字仅代表当时基线，最新口径以根目录 `README.md` 与 `CHANGELOG.md` 为准。


## 1. 测试范围

覆盖房间/座位状态、封禁生命周期、批量建座、现场违约幂等、资源显示、数据库约束，以及 B 与 C/A/D 的集成。

## 2. 测试环境及依赖

- 代码基线：`D:\seat_clean_baseline`（公共底座 + D 模块整改后），当前完整测试 **380 passed, 1 skipped**。
- pytest 8.3.4、FastAPI TestClient、临时 SQLite。
- 运行目录：`SR`。
- 命令示例：

```bash
python -m pytest tests/test_resource_lifecycle.py tests/test_safety_fixes.py tests/test_api.py -q
```

- M-04 跨模块测试使用 B 的 `release_affected_reservations` helper 和临时预约夹具，不依赖 C 分支已合并；最终跨模块验证见文档 11。
- **M-04 统一断言：** 预约 `cancelled`、`end_reason="resource_unavailable"`、不 `no_show`、不扣信用。

## 3. 测试数据准备

- 临时 DB；若使用 `ctx` 夹具，必须使用 `helpers.seed_fixture` 的 `S1~S5/T1/A1/Y1/R1/R2`。
- 若使用本文示例的 `A101/B201/A9001/Y0001/S2023001`，必须显式初始化 `demo=True` 的独立测试库，不得与 `ctx` 夹具混用。
- 预约：通过 C engine/测试夹具创建未来 `pending`、当前 `in_use`、`away` 各一条。
- 封禁：未来/生效/已释放各一条。
- 不使用生产数据库。

## 5. 详细测试样例

### B-SEC-001 封禁状态机单元测试

- **测试类型：** 单元
- **对应审计问题：** L-08 / 既有封禁基线
- **测试目的：** 验证 available/maintenance/disabled、未来封禁、多封禁、手工维护的恢复规则。
- **前置条件：** `resource_rules` 纯函数。
- **测试步骤：**
  1. 对 available 座位施加当前封禁/未来封禁。
  2. 对手工维护、disabled、多封禁座位关闭封禁。
  3. 检查 `seat_state_after_block(s)` 结果。
- **输入数据：** `Seat(admin_status=..., maintenance_by_block=...)`；`SeatBlock(start_at,end_at)`。
- **预期结果：** 未来封禁不立即改状态；当前封禁进入 maintenance 且 `maintenance_by_block=True`；手工维护/disabled 不自动恢复；多封禁全部关闭后才按规则恢复。
- **测试方式：** pytest 单元。
- **优先级：** P2

### B-SEC-002 批量建座 ID/数量规则单元
