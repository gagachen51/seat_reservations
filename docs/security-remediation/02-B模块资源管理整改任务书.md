# B 模块资源管理整改任务书

## 1. 模块职责

B 负责自习室、座位、资源状态、封禁生命周期及相关资源治理：

- 房间创建/修改/关闭。
- 座位创建/修改/停用/维护。
- 座位封禁/解封/封禁记录。
- 批量建座。
- 停用影响预览。
- 资源相关数据库约束与迁移。
- 资源页面与现场座位处置。

## 3. 问题逐项说明

### M-04 房间关闭/座位停用后已有预约未处理（B 资源主责）

#### 现状

- `update_room(status="closed")` 只保存 room.status，不取消/释放/通知已有预约。
- `update_seat(admin_status="disabled"/"maintenance")` 只保存座位状态，不处理已有预约。
- 签到路径会拒绝关闭房间/停用座位；超时 sweep 会把仍 pending 的预约标记 `no_show` 并扣信用。
- `block_seat` 已有正确模式：找出重叠预约、取消、通知、审计；资源状态更新没有复用。
- 已通过临时数据库复现：创建未来预约 → 关闭房间 → 预约仍 pending → sweep 后 no_show、信用下降。

#### 具体修改要求

1. **固定 M-04 契约（不再另行选择状态）：**
   - B 在 `engine.py` 实现统一 helper：
     `release_affected_reservations(room_id, seat_id, reason, actor, now)`。
   - 受影响预约统一置为 `cancelled`，`end_reason="resource_unavailable"`。
   - 不得判 `no_show`、不得扣信用。
   - 对 `pending/in_use/away` 均按该 helper 处理；C 直接调用，不重复实现资源停用入口。
2. 在 `update_room`/`update_seat` 中调用该 helper：
   - 查询受影响预约。
   - 释放/取消，不记违约、不扣信用。
   - 写入通知。
   - 使用 `self.audit_event(...)` 写审计，不得修改审计签名。
3. 事务要求：房间/座位状态更新、helper 处理预约、通知/审计必须在同一个写事务中；任一失败整体回滚。
4. 操作应可重复：重复关闭/重复停用不应重复取消或产生重复通知/审计异常。
5. 停用影响预览 `GET /admin/rooms/{id}/impact` 继续只读，不得在预览时副作用；真正执行时才处理。
6. 保留 `block_seat` 现有封禁语义，不要用资源停用逻辑覆盖封禁到期恢复规则。

#### 涉及文件/接口

- `SR/src/seat_reservation/domain/engine.py:2318-2363`（`update_room`）
- `SR/src/seat_reservation/domain/engine.py:2439-2508`（`update_seat`）
- `SR/src/seat_reservation/domain/engine.py:1429-1511`（`block_seat` 参考实现）
- `SR/src/seat_reservation/domain/engine.py:1286-1402`（sweep 参考）
- `SR/src/seat_reservation/api/routes/admin_routes.py:156-176,210-232`
- `SR/src/seat_reservation/api/routes/resource_routes.py:120-127`
- 测试：`tests/test_resource_lifecycle.py`、`tests/test_safety_fixes.py`

#### 修改边界

- B 负责 `update_room`/`update_seat` 的资源侧实现和测试。
- 预约状态/信用/no_show 规则的具体语义必须与 C 共同确认；C 负责预约状态转换和 sweep 侧测试。
- 不修改 `_check_in_core` 的签到业务，除非契约要求；签到拒绝逻辑由 C 维护。
- 不改变既有封禁/解封状态机（`maintenance_by_block`）的语义。

#### 协作要求

- C：直接调用 B 的 `release_affected_reservations` helper；统一断言 `cancelled`、`end_reason="resource_unavailable"`，不重复实现资源停用入口。
- 共享层：确认通知/审计接口可用；不改认证。
- A：如果账号/学生视图展示受影响预约，确认状态标签不需要新增不兼容值。

#### 验收标准

- 关闭房间后，已有 pending 预约不再进入 no_show；学生信用不因管理员关闭资源而下降。
- 停用/维护座位后，已有预约统一 `cancelled`、`end_reason="resource_unavailable"` 并通知。
- 重复关闭/停用不重复产生副作用。
- 房间/座位状态与预约状态一致；影响预览无副作用。
- 对应 B/C 测试通过。

### M-05 现场违约登记可重复执行

#### 现状

- `manual_violation(actor, reservation_id, "warn", note, now)` 每次调用都插入一条 `MANUAL_INSPECTION` 违规并扣信用。
- 没有同一预约/同一违约类型的幂等/去重限制。
- 已复现：同一 in_use 预约连续两次 warn，信用 100 → 90。

#### 具体修改要求

1. 明确同一预约、同一违约类型的重复登记策略，建议二选一：
   - 第二次返回 409 `DUPLICATE_VIOLATION`，不新增违规、不扣分；或
   - 第二次幂等成功，返回已有违规，不新增记录/不扣分。
2. 在 `manual_violation` 内检查已有有效 `MANUAL_INSPECTION` 记录（按 reservation_id + type + status/source 维度），并保持事务原子性。
3. 对 `mode="release"` 也要防止重复释放/重复扣分；第二次应返回明确业务错误。
4. 保留每次合法巡检的审计；重复请求可以记录“重复被拒绝”事件，但不得重复扣信用。
5. 明确前端/接口错误码，便于页面提示。

#### 涉及文件/接口

- `SR/src/seat_reservation/domain/engine.py:1839-1889`
- `SR/src/seat_reservation/storage/repository.py` 违规查询方法
- `SR/src/seat_reservation/api/routes/admin_routes.py:235-251`
- `SR/src/seat_reservation/web/app.js` 现场处置/违约提示
- 测试：`tests/test_safety_fixes.py`、`tests/test_resource_lifecycle.py`

#### 修改边界

- B 负责现场违约幂等实现和资源侧测试。
- 不改变既有违规扣分参数（`credit.penalty.manual_inspection`）和自动黑名单规则。
- 若需要新增唯一索引，属于 L-07，需考虑历史数据兼容，不能直接破坏已有重复记录。

#### 验收标准

- 同一预约同一类型重复 warn 不会重复扣分/新增违规。
- 第二次请求有明确 4xx 或幂等响应，不静默重复。
- release 重复调用不重复释放/扣分。
- 原有单次违约、信用扣分、审计行为不变。

### L-07 数据库约束与一致性（B 资源/库主责）

#### 现状

- `reservation_slots.seat_id/user_id` 无 FK，未强制与父 reservation 一致。
- `seats` 只有全局 id PK，没有 `(room_id, 座位编号)` 自然键；管理员可用不同 id 建语义重复座位。
- `waitlist.start_slot/end_slot` 只有 `end > start` CHECK，没有 0..47 范围。
- `complaints.seat_id/reservation_id` 无 FK。
- 当前代码未发现直接远程可利用路径，但未来代码/手工 SQL 可能产生孤儿/矛盾数据。

#### 具体修改要求

1. 使用已预留的 **`RESOURCE_MIGRATION_VERSION = 4`** 新增约束；`v3` 保留给共享层审计，不得占用。
   - `reservation_slots` 与 reservations/seats 的一致性约束（组合 FK/触发器/写入校验，按 SQLite 能力选择）。
   - `seats` 自然键：如果业务要求房间内编号唯一，新增 `UNIQUE(room_id, seat_number)` 或等价约束；需先确认现有数据/座位 ID 规则。
   - `waitlist` slot 0..47 CHECK。
   - complaints 的 seat/reservation FK（如业务允许空，使用 nullable FK）。
2. 迁移必须兼容已有数据：先清理/校验，再新增约束；不得直接导致现有生产库迁移失败。
3. 更新 `storage/migrations.py` 和初始化 schema；增加迁移幂等测试。
4. 对新增约束设计测试：孤儿插入、重复自然键、非法 slot 应被拒绝。
5. 与 C 共同确认 `reservation_slots` 事务/父子一致性；C 负责预约事务侧测试。

#### 涉及文件/接口

- `SR/src/seat_reservation/storage/migrations.py`
- `SR/src/seat_reservation/storage/repository.py`
- `SR/src/seat_reservation/domain/engine.py` 资源/预约写入路径
- 测试：`tests/test_resource_lifecycle.py`、`tests/test_concurrency.py`

#### 修改边界

- B 主责 schema/迁移和资源表约束；C 协作预约 slot/事务。
- 不在本任务中直接改生产数据库；只提交迁移和测试。
- 不删除已有座位/预约数据；如需数据清理，另立迁移/运维步骤。

#### 验收标准

- 新库和旧库升级都能成功迁移。
- 违规孤儿/重复/非法 slot 写入被数据库拒绝。
- 现有 **380 passed, 1 skipped** 基线不回归。
- 约束错误被转译为明确 409/422，不泄露 SQL。

### L-08 关闭房间座位显示与预约 ID 暴露

#### 现状

- `seat_views` 不按 `rooms.status` 过滤，关闭房间的座位可能显示 available。
- `holder_reservation_id` 返回给所有认证用户；学生可看到他人的预约 ID。
- 未发现使用该 ID 越权读取/修改，但属于信息暴露和显示误导。

#### 具体修改要求

1. `seat_views` 在房间 `closed` 时：
   - 座位状态显示为不可用/关闭，或按产品约定不返回；不能显示 available。
   - 预约创建仍应拒绝关闭房间（现有 `create_reservation` 已检查）。
2. 按角色最小化 `holder_reservation_id`：
   - 学生不返回他人预约 ID。
   - 管理员/座位当前持有人按业务需要可返回。
3. 保持座位查询正常业务：学生仍能看到座位状态/是否可用/房间信息。
4. 更新前端图例/状态标签，避免新增状态没有文案。

#### 涉及文件/接口

- `SR/src/seat_reservation/storage/repository.py:400-487`
- `SR/src/seat_reservation/domain/models.py:437-453`
- `SR/src/seat_reservation/domain/engine.py:553-587`
- `SR/src/seat_reservation/web/app.js` 座位视图
- 测试：`tests/test_api.py`、`tests/test_safety_fixes.py`

#### 修改边界

- B 主责 repository/seat view；C 确认预约状态派生不被破坏。
- 不改变座位预约冲突查询；只改展示/返回字段。
- 如果隐藏 holder ID 影响现场管理，按角色条件返回，不全局删除。

#### 验收标准

- 关闭房间的座位不再显示 available。
- 学生看不到他人 holder reservation ID；管理员必要场景仍可用。
- 正常开放房间座位查询、预约、签到不受影响。
