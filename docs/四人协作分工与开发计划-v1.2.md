## 0. 结论摘要

1. **当前项目不是“需要从零开发”的半成品，而是一套已经完成交付的 v2.0 系统。** 实际代码包含 77 个 HTTP 接口、17 张业务表；当前最终发布基线为 **v2.0.3**，自动化测试 **499 passed, 1 skipped**（本文其余章节的 115/475 等数字为当时历史基线）。
2. **因此四人分工不能按“A 做用户、B 做资源、C 做预约、D 做运营”重新实现一遍。** 那样会大量重复已有功能，违反“不为了增加工作量而重复实现已有功能”的原则。正确做法是把四个模块各自拆出一个**真实缺口明显的纵向增量**，每个人都完成“后端规则 + 接口 + 前端 + 测试”的闭环。
3. **本轮建议的四个增量是：**
   - **成员 A：账号生命周期、登录设备与个人中心**——把目前只能在命令行完成的建号、停用、重置密码、会话管理搬进 HTTP API 和管理界面，补个人资料维护；同时承接学生端“我的候补”展示页面（调用 C 提供的候补接口）。
   - **成员 B：资源与座位治理**——修复座位封禁“永久变维护、到期不自动恢复、未来封禁立即生效”的实际缺陷，补封禁列表、批量建座、停用影响预览和跨自习室移动保护；承担架构文档与共享文件守门。
   - **成员 C：预约核心增强**——实现文档中明确未完成的“续约（延长时段）”，并补齐候补取消接口；学生端“我的候补”页面交由 A 实现，避免 C 同时承担核心规则、前端、测试规范和 CI。
   - **成员 D：运营分析与报表**——补任意日期区间的运营分析、图表页面和管理端候补队列视图，扩展 CSV 导出类型，修复现有导出忽略日期筛选的问题；承担 CI 工作流。
4. **基础设施已重新分散**：B 负责架构、迁移、共享文件守门和公共测试夹具；C 只负责测试规范与预约并发测试，不再负责 CI、公共夹具和所有模块的测试；D 负责 CI；A 负责账号/个人中心前端；每个成员都保留自己的后端、前端、测试交付物。
5. **发现 4 处业务规则与代码不一致，必须先确认，不能直接按新说法改代码**：
   - “08:00—22:00 共 14 个时段”与代码的“07:00—23:00、30 分钟粒度、48 个时段”不一致；
   - “当天至未来第 3 个自然日”与代码及 SRS 已确认的“7 天（含当日）”不一致；
   - “最多 2 条有效预约”与代码及 SRS 的“每人每天最多 2 个、当日总时长 4 小时”不一致；
   - “提前 15 分钟签到不代表提前获得使用权”与代码“签到成功立即转为使用中”不一致。
6. **另有 1 处规则需要明确边界**：“资源停用时保留已有预约，不自动取消”目前只对“座位管理状态改为停用”和“自习室关闭”成立；座位封禁（维护）会按 BR-09 自动取消受影响预约。两种“停用”是否同一口径，需要确认。
7. **数量已重新核对**：现有接口 62 个、业务表 17 张、参数 34 项、现有导出 3 类；本期计划新增 15 个路由（A 个人资料、B 批量建座、B 停用影响预览为可选，最低必交 12 个），导出扩展为 7 类（原 3 + 新 4），不新增业务表。
8. **B 的迁移方案改为“零回填”**：新增 `seats.maintenance_by_block` 默认 0，**不根据现有 `admin_status` 猜测历史维护原因**；所有历史维护一律视为“手工维护”，不会在封禁到期时自动恢复。只有新流程明确标记为“封禁管理”的座位才自动恢复，并保留管理员显式恢复入口。
9. **v1.2 新增集成分支 `integration/v1.2`**：四个 `feature/*` 分支均从该集成分支创建，PR 先合入集成分支；最终通过 `integration/v1.2 → main` 的发布 PR 合并，`main` 全程禁止直接 push，不用“集成”作为绕过分支保护的例外。
10. **B 的共享文件集成提交不落在 main**：B 在 `chore/shared-integration` 分支应用 SFCR，PR 合入 `integration/v1.2`；集成分支再统一验证、统一发布。
11. **SFCR 有模板、时限、升级和登记表**：B 正常是共享文件唯一修改人；B 超过 1 个工作日未处理时，由负责人授权备份处理人，不能因 B 忙于业务而长期阻塞。
12. **代码分区精确到方法锚点**：`engine.py`、`repository.py` 每个成员只允许新增指定方法，插入到指定现有方法之后/章节锚点之前；禁止在文件末尾追加，禁止改他人分区。
13. **B 的迁移边界补全 7 种状态组合**：尤其 `disabled` 座位不会被封禁到期错误恢复为 `available`；新增 Q-16 待负责人确认技术口径，并附升级后历史维护座位人工核对清单。

## 4. 当前代码结构及主要问题

### 4.1 分层与调用链

```text
浏览器 / 桌面壳
   │  HTML + app.js（单页，hash 路由，fetch + CSRF）
   ▼
api/（app.py 中间件、deps.py 依赖、routes/ 四组路由）
   │  get_actor / read_engine / write_engine / render
   ▼
domain/（DomainEngine：全部业务用例与规则判定）
   │  只依赖 ports.Repository 协议
   ▼
storage/（SqliteRepository + migrations + seed）
   │  BEGIN IMMEDIATE 写事务 / BEGIN 读事务
   ▼
SQLite（WAL、busy_timeout、17 张业务表）
```

关键约定（新功能必须遵守）：

1. **业务规则只写在 `domain/`**，路由层只做参数形状和 HTTP 映射；不要把规则散落到路由。
2. **拒绝且无副作用**：参数/权限/状态错误抛 `AppError`，事务回滚；需要“拒绝但保留业务后果”时返回 `Result.failure`（409），由外层提交。
3. **时间由调用方注入 `now`**，领域层不读系统时钟，保证测试可复现。
4. **仓储方法不自行提交事务**，由 `AppContext.engine()` 统一开启/提交。
5. **响应统一为** `{"ok": true, "data": ..., "message": ...}` 或 `{"ok": false, "error": {"code", "message", "rule", "details"}}`。
6. **所有写请求需要 CSRF**：`X-CSRF-Token` 必须等于可读 Cookie `seat_csrf`。

## 5. 四人开发分工方案

### 5.1 分工原则

1. **一人一个纵向模块**：从领域规则、仓储、接口、前端到测试，成员独立完成，不把某一层整体切给别人。
2. **每个人必须有可运行的代码成果**：后端接口 + 前端入口 + 测试，三者缺一不可；文档只写自己模块的设计说明。
3. **不重复实现已有功能**：只做第 3 节列出的真实缺口。
4. **不破坏既有规则**：现有 115 个测试必须继续通过；涉及规则口径的改动先确认。
5. **共享文件最小化**：新文件优先；必须改共享文件时按第 8 节的“文件所有权与合并顺序”执行。

### 5.2 四人模块与角色

| 成员 | 模块 | 核心增量 | 兼任角色 |
|---|---|---|---|
| **成员 A** | 账号与个人中心 | 账号生命周期 API、会话管理、个人资料；学生端“我的候补”展示页（调用 C 的候补接口） | 账号模块设计说明；个人中心前端 |
| **成员 B** | 资源与座位治理 | 封禁生命周期修复、封禁列表、批量建座、停用影响预览、座位移动保护 | **架构牵头**；共享文件（app.py/ports/models/migrations/公共夹具）唯一修改人 |
| **成员 C** | 预约核心增强 | 续约（延长时段）、候补取消接口；预约并发测试 | **测试牵头**：测试规范、预约并发用例；**不负责** CI、公共夹具和其他模块的测试 |

### 5.3 为什么这样分是均衡的

- 四个模块都**同时包含后端规则、HTTP 接口、前端页面、测试**，没有“只写文档”或“只改 README”的角色。

- 候补功能按“领域/API 归 C、学生展示归 A、管理端展示归 D”拆分；接口契约在 Phase 0 冻结，三方按契约并行，避免互相等待。

#### 数据任务

- 迁移 v2：`seats.maintenance_by_block`，默认 0；**不做任何回填**。
  - 历史数据中 `admin_status='maintenance'` 的座位，无论是否有旧封禁记录，一律视为“手工维护”（`maintenance_by_block=0`）。
  - 旧封禁到期/释放时不会自动恢复这些座位；管理员必须通过 `PUT /admin/seats/{id}` 或 `release` 的 `restore_seat=true` 显式恢复。

- `block_seat` 新语义（按“是否手工维护/停用”分支，避免猜测）：
  - 先判断 `manual_maintenance = (seat.admin_status == 'maintenance' and not seat.maintenance_by_block)`；
  - 插入封禁记录；
  - 若 `manual_maintenance` 为真：**不改** `admin_status`、**不改** `maintenance_by_block`；封禁记录仍参与 `seat_views` 的时间窗派生与预约取消；
  - 若 `seat.admin_status == 'disabled'`：**不改** `admin_status`；把 `maintenance_by_block` 置 **0**；封禁只通过 `seat_views` 的时间窗生效，**绝不允许封禁到期把 disabled 恢复为 available**；
  - 否则（available，或由封禁管理的 maintenance）：把 `maintenance_by_block` 置 1；**仅当封禁区间覆盖当前时刻**才把 `admin_status` 设为 `maintenance`；未来封禁不改当前 `admin_status`，由 `seat_views` 按时间窗派生维护状态；
  - 受影响预约仍按 BR-09 取消并通知（本期不改变 BR-09 口径，是否把“停用”与“封禁”统一列入 Q-08）。
- 到期/解封：关闭记录；若 `maintenance_by_block=1` 且该座位无其他生效封禁：
  - 若 `admin_status == 'maintenance'`，恢复 `available`；
  - 若 `admin_status == 'disabled'`，**保持 disabled**；
  - 若 `admin_status == 'available'`，不改状态；
  - 无论是否恢复，都把 `maintenance_by_block` 归零；
  - `maintenance_by_block=0` 的手工维护/停用一律不自动恢复。
- `update_seat` 只要管理员显式传入 `admin_status`，就把 `maintenance_by_block` 清零，表示手工意图优先；之后再到期封禁也不会覆盖。
- **未来封禁期间 `admin_status` 可能仍为 `available`**：维护态由 `seat_views` 按封禁时间窗派生；管理端列表/现场页必须同时展示封禁记录，不能只看 `admin_status` 误判座位可用。这是 v1.2 明确的展示口径，不改变学生端可用性判断。
- 定时扫描 summary 增加 `seat_blocks_expired`。

**迁移安全性论证（针对误恢复风险）**：

1. v1 的 `seats` 没有记录“维护来源”，无法区分“管理员手工设为维护”和“旧封禁流程设为维护”。
2. 因此 v2 **只加列、不回填**：默认 `maintenance_by_block=0`，历史维护一律按手工维护处理。
3. 旧封禁释放/到期时，因为标记为 0，不会自动恢复座位；管理员必须显式 `restore_seat=true` 或 `PUT /admin/seats/{id}`。
4. 只有新封禁流程在确认“当前不是手工维护”后才写 1；`update_seat` 手工设置又会清零。
5. 代价是升级后需要一次性人工核对历史维护座位；收益是**绝不会把手工维护座位误恢复**。测试任务第 3、4、5 条专门覆盖这一点。

#### 分析指标建议

- **KPI**：预约数、完成数、违约数、取消数、签到率、违约率、平均使用时长、平均评分、投诉办结率。
- **daily**：按日 `reservations/completed/no_show/cancelled/checkins`。
- **peak_hours**：按开始时段聚合预约量、平均时长；用于峰值图。
- **rooms**：按自习室聚合预约数、完成率、违约率、使用率、平均评分。
- **violations**：按日期/类型聚合。
- **ratings**：1～5 星分布与平均分。
- **waitlist**：`queued/notified/confirmed/expired/cancelled` 漏斗与确认率。
- **complaints**：办结数、平均处理时长（小时）、平均满意度。
- **使用率口径**：`已占用 slot 数 / (座位数 × 开放 slot 数)`，按房间开放时间计算；在文档中写明近似口径，避免与看板“当前时刻使用率”混淆。

#### 数据任务

- 只读查询：`reservations`、`reservation_slots`、`rooms`、`seats`、`violations`、`complaints`、`reviews`、`waitlist`、`users`。
- **不新增表、不加迁移**。
- 7 类导出统一走 `storage/export_queries.py`，避免改 C 的 `list_waitlist`、A 的用户查询等分区；所有文本继续走 `_csv_safe` 防公式注入。
- 修复 `admin_stats` 中 `open_complaints`、`waitlist_waiting` 不按房间过滤的问题。

#### 测试任务

1. 构造跨 3 天的预约/违约/投诉/评价/候补数据，断言 KPI、daily、peak、rooms 的精确值。
2. 日期区间：默认 7 天；边界包含首尾；倒置/超过 90 天拒绝；空区间返回 0 而非报错。
3. 房间筛选：只统计目标房间；投诉/候补 KPI 也随房间变化。
4. 权限：学生/教师 403；room_admin/sys_admin 200；系统管理员可看全部。
5. 导出：7 类列头/行数正确；`date_from/date_to` 对 7 类都生效。
6. CSV 注入：以 `= + - @` 开头的文本被加前导单引号。
7. 契约：新路由无 5xx；未知导出类型 422；错误结构统一。
8. 回归：现有 `/admin/stats` 返回键不减少，概览页仍可用。

#### 验收标准

- 分析接口可按日期区间/房间返回完整指标；前端图表可切换 7/30/90 天。
- **7 类导出**（原 3 + 新 4）均可用，日期筛选真实生效。
- 房间筛选下 KPI 一致，不再出现“全局投诉数”。
- 权限与 CSV 安全测试通过。
- 现有看板与 115 个测试不回归。
- CI 在 Windows/Ubuntu 上可跑通 `pytest -q`。
- 管理端候补队列为**可选增强**；时间不足可降级，但分析、导出、CI 为必交。

#### 估时与代码量

后端约 400～500 行，前端约 300～400 行，测试约 250～350 行，文档约 80～120 行，CI 约 0.5 个工作日；净开发约 4～5 个工作日，加联调/回归/缓冲约 3～4 个工作日，合计约 **9 人日**。

### 7.2 测试规范（C 牵头制定，写入 `docs/collaboration/测试规范.md`）

### 8.7 共享文件变更请求（SFCR）流程（v1.2 补全）

#### 8.7.1 统一模板

每个 SFCR 必须在 PR 评论或 issue 中使用以下模板，缺项视为无效请求：

```text
SFCR-<模块>-<三位序号>（例：SFCR-A-001）
申请人 / 模块 / feature 分支：
目标文件：
目标锚点（方法名或章节注释，必须来自当前源码）：
修改前代码（before，带足够上下文）：
精确 diff（after，必须可直接 apply）：
修改理由：
为什么不能用新文件/局部模型替代：
关联测试（文件/用例名）：
预期结果（命令 + 期望输出）：
风险与回滚：
是否需要迁移/参数/协议变更（是/否 + 说明）：
B 处理人 / 应用提交 SHA：
发起人复核（diff/测试/结论）：
最终状态（open / applied / rejected / backup-applied / reverted）：
```

要求：

1. **精确 diff**：不能写“请在 app.py 加一行”，必须给出 `import` 与 `include_router` 的确切位置、上下文和完整行。
2. **修改理由**：说明为什么必须改共享文件；能放新文件、局部模型或测试文件的，不允许提 SFCR。
3. **关联测试**：至少列出要跑的测试文件/用例；新增路由还要列入 `test_new_routes_contract.py`。
4. **预期结果**：写明命令（如 `python -m pytest tests/test_account_api.py -q`）和期望输出；不能只写“应该没问题”。
5. **锚点来自源码**：目标锚点必须是当前仓库中存在的方法/章节注释，不能虚构。

#### 8.7.2 B 的处理时限与升级

| 时间 | 动作 |
|---|---|
| T+4 小时 | 申请人在 PR/IM 提醒 B；B 确认已收到 |
| T+1 个工作日 | B 必须在每日 **17:00 集中处理**一批 SFCR；处理结果写入登记表 |
| T+1 个工作日仍未处理 | 升级给项目负责人；负责人授权**备份处理人** |
| 备份处理 | C 可处理 `engine.py`/`repository.py`/`ports.py`；D 可处理 `app.py`/`app.js`/CI；A 只处理文档，**A 仍不得直接改 app.py** |
| 备份后 | 备份提交标注 `[backup]`；B 在 1 个工作日内补审；B 不认可则回滚，重新走 SFCR |

> B 必须为 SFCR 预留每天 17:00–17:30，不得以“自己的业务开发忙”为由长期不处理。若 B 当天确实无法处理，应提前在群里指定 C 或 D 为临时备份，并在登记表记录。
>
> **分支卫生**：每批 SFCR 开始前，`chore/shared-integration` 从最新 `integration/v1.2` 重建（或 rebase）；PR 合并后删除该分支，下一批重新创建。不要长期复用一条已合并的集成分支，避免把旧提交带回。`chore/shared-integration` 只放**其他成员的 SFCR 与跨模块共享变更**；B 自己的 `resource_routes`、`app.py` 资源 router 注册随 `feature/resource-module`，不要混进 chore 分支。

#### 8.7.3 应用后复核

1. B 应用 SFCR 后，在 PR 评论中回复应用提交 SHA 与 diff 链接。
2. 发起人必须在 **半个工作日**内复核：
   - diff 是否与申请一致；
   - 是否误改他人分区；
   - 关联测试是否通过；
   - 是否影响现有 115 个测试。
3. 发起人回复 `SFCR-xx 验收通过` 或 `不通过：<原因>`。
4. 不通过时 B 在 1 个工作日内修正或回滚；回滚后该功能 PR 不得合并。
5. 涉及测试规范的由 C 复核；涉及 `app.js` 注册表的由 A 复核；涉及 `app.py` 的由 A 复核 B 的 PR。

## 9. GitHub 分支与 Pull Request 工作流程

### 9.1 分支结构（v1.2 明确到“从哪来、往哪去”）

| 分支 | 创建来源 | 用途 | PR 目标 | 保护/权限 |
|---|---|---|---|---|
| `main` | — | 稳定发布 | — | **禁止直接 push、禁止 force push、禁止绕过保护**；只接受发布 PR；2 approvals + CI |
| `integration/v1.2` | 从 `main` 创建（Phase 0） | 本轮集成分支，承载四个模块与 SFCR 集成 | 最终发布 PR → `main` | 禁止直接 push；PR 合入；1 approval + CI；共享文件 PR 需 B approve（B 为作者时由 A/C/D 中一人 approve） |
| `chore/shared-integration` | 从 `integration/v1.2` 创建 | B 应用 SFCR 的专用分支 | → `integration/v1.2` | 仅 B 推送；PR 由 A/C/D 中至少 1 人 approve；B 不得自审自合 |
| `feature/account-module` | 从 `integration/v1.2` 创建 | A 的账号与个人中心 | → `integration/v1.2` | 个人分支；A 推送；PR 审核 |
| `feature/resource-module` | 从 `integration/v1.2` 创建 | B 的资源与座位治理 | → `integration/v1.2` | 个人分支；B 推送；PR 审核 |
| `feature/reservation-module` | 从 `integration/v1.2` 创建 | C 的预约核心增强 | → `integration/v1.2` | 个人分支；C 推送；PR 审核 |
| `feature/analytics-module` | 从 `integration/v1.2` 创建 | D 的运营分析与报表 | → `integration/v1.2` | 个人分支；D 推送；PR 审核 |
| `hotfix/<name>` | 从 `main` 创建 | 线上紧急修复 | → `main`，之后 cherry-pick 回 `integration/v1.2` | 2 approvals + CI；不得直接 push main |

**回答六个执行问题**：

1. **四个人从哪个基础分支创建 feature 分支？** 都从 `integration/v1.2` 创建，不从 `main` 创建；这样共享锚点、CI 和契约先就位，避免 feature 分支各自基于不同基线。
2. **分支名是否保持？** 保持 A `feature/account-module`、B `feature/resource-module`、C `feature/reservation-module`、D `feature/analytics-module`。
3. **是否增加集成分支？** 增加 `integration/v1.2`（与计划版本一致；若团队坚持叫 `integration/v1.1`，名称可替换，流程不变）。
4. **B 的共享文件集成提交落在哪？** 落在 `chore/shared-integration`，通过 PR 合入 `integration/v1.2`；**不落在 main**，也不由 B 直接 push 集成分支。
5. **每个 PR 合并到哪？** 四个 feature PR、B 的 SFCR PR 全部合并到 `integration/v1.2`；不直接合 main。
6. **最终如何进 main？** 集成分支通过全量测试与验收后，开 `integration/v1.2 → main` 的发布 PR；2 approvals + CI + 分支保护通过后合并，打 tag。
7. **如何禁止绕过？** `main` 与 `integration/v1.2` 都开启分支保护：禁止直接 push、禁止 force push、要求 PR、要求 CI、要求最新分支、禁止管理员绕过（"Do not allow bypassing the above settings"）。任何“为了方便集成”的直接 push 都视为违规，回滚并重做 PR。

### 9.1.1 分支操作顺序（从零到发布）

```text
1. 确认基线：main 在 d65667b，工作区干净；四人确认 v1.2 计划与接口契约。
2. B 从 main 创建 integration/v1.2（仅建分支，不改业务代码；此时先不开启“必需 CI”保护，避免 workflow 尚未存在时自锁）。
3. D 在 integration/v1.2 上通过 PR 加入 CI/PR 模板（chore/ci-bootstrap → integration/v1.2）；合并后在 GitHub 开启 integration/v1.2 的分支保护（PR、CI、up-to-date、禁 force push）。
4. B 从 integration/v1.2 创建 chore/shared-integration，加入 engine/repository 分区锚点（仅注释/空分区，不含业务逻辑），PR → integration/v1.2。
5. A/B/C/D 各自从最新的 integration/v1.2 创建四个 feature 分支。
6. 开发期间：成员提交 SFCR → B 在 chore/shared-integration 应用 → PR → integration/v1.2；合并后各 feature 分支 rebase 到 integration/v1.2。
7. 功能 PR：按 B(resource) → A(account) → D(analytics) → C(reservation) 的顺序合入 integration/v1.2；每个 PR 1 approval + CI，共享文件由 B approve（B 为作者时由 A/C/D 中一人 approve）。
8. 集成分支每日/每合并后跑全量 pytest；D 维护 CI 绿灯；C 维护新路由契约冒烟。
9. 全部功能合入且 D10-D11 回归通过后，开 integration/v1.2 → main 发布 PR：2 approvals + CI + 无未解决评论。
10. 发布 PR 合并后打 tag（如 v2.1.0）；hotfix 从 main 拉出，PR 回 main 后再 cherry-pick 回 integration/v1.2。
```
